# UI upload of custom docker-compose deployment plans (review pass v1)

Adds a self-service capability to upload a docker-compose file as a new deployment plan from the UI. A user provides a compose file plus a name (and a required GPU `instanceType` from an allowlist, with optional `modelName`/`description`); the API Lambda stores the compose content in the S3 compose bucket and the plan metadata in a new DynamoDB table (`TpotDeploymentPlanTable`, pk `planId`). At read time these user plans (`source='user'`) are merged with the code-defined built-ins (`source='builtin'`), with built-ins winning on id collision, so uploaded plans become selectable for booking without a CDK redeploy while the built-in default set stays code/CDK-managed. The deployer resolves `composeFile`/`modelName` for user plans directly from the plan record (it can't import the API modules) and keeps hardcoded resolution for built-ins.

Watch for: the compose payload is executed on a GPU host via SSM, so this is a code-execution surface gated only by Basic auth — the guardrails (allowlist, size cap, slug sanitization) are enforced, but YAML validation degrades to a near-no-op when PyYAML isn't bundled (confirmed). The frontend surfaces a generic "Conflict" instead of the API's specific 409 message on duplicate/collision (likely). A user-supplied `recipe` is accepted and persisted but never consumed by the deployer (confirmed, minor).

**Verdict**: NEEDS_CHANGES

## High-level view

The dynamic layer treats DynamoDB as an additive, fail-open source: `get_all_plans()` and `get_plan()` return built-ins first, and a missing table or access error degrades to built-ins only — the right posture for keeping bookings working when the table isn't yet provisioned. Built-ins win on id collision in both the read path and the create path.

The API↔CDK contract lines up: the new table, its `planId` pk, the `COMPOSE_BUCKET`/`DEPLOYMENT_PLAN_TABLE` env vars on both Lambdas, the three routes (`GET`/`POST /deployment-plans`, `DELETE /deployment-plans/{planId}`) with matching router branches, and IAM (S3 write for the API, DynamoDB rw for the API, `GetItem` + S3 `GetObject` for the deployer) are all present and consistent.

The deployer change is scoped so that user plans are detected as ids absent from the hardcoded `plan_compose_map`, and only then does it read the record for `composeFile`/`modelName`. Built-in ids never touch the new lookup, and the existing S3-first `_load_compose_content` makes an uploaded file usable by filename with no further change.

Security guardrails are enforced in `create_deployment_plan` — instanceType allowlist, 512 KB cap, slug-based `planId` with a derived filename that can't traverse S3 keys, built-in and existing-user collision checks. The weak spot is YAML validation, which becomes a structural guess when PyYAML is unavailable, letting almost any text through. Given the compose file is later executed on a GPU host, that is the most notable gap, though the feature is admin-only behind Basic auth.

The frontend wiring (nav item, route, upload page, source-based delete gating, dynamic plan pickup on BookingPage) is coherent. The main rough edge is error surfacing: the shared client intercepts every 409 as a generic `Conflict` error, so the upload form can't show the specific reason a plan id was rejected.

<summary>Issues (5)</summary>

1. **YAML validation fallback is a near-no-op** — when PyYAML isn't in the Lambda bundle, `_validate_compose_content` accepts any document containing the substring `services` or any line with a `:`. Bundle PyYAML (or validate for a top-level `services` mapping) so the check is real before content is executed on a host.
2. **409 error detail lost in the client** — `request()` throws a generic `Error('Conflict')` for all 409s, so PlansPage shows "Conflict" instead of the API's "collides with a built-in" / "already exists; set overwrite=true" message. Surface `error.data.error` on the plans page, or return the specific message.
3. **Orphaned S3 object on failed metadata write** — create writes the compose object to S3 before `put_item`; if `put_item` fails the object is left behind under `compose-files/user-<planId>.yaml`. Delete the object on the table-write failure path, or write the table first.
4. **`recipe` is accepted and stored but never used** — the deployer reads only `composeFile`/`modelName` from the plan record and never references `recipe`; the API defaults/persists it regardless. Drop it from the create surface or wire it into the deployer, otherwise it misleads.
5. **DELETE path id not URL-encoded** — `deleteDeploymentPlan` interpolates `planId` straight into the path. Safe today because ids are slugified to `[a-z0-9-]`, but encode it to stay correct if id derivation ever loosens.

### Built-in vs user merge and collision handling

`get_all_plans()` emits the built-ins first, records their ids, then appends user plans while skipping any whose id is already a built-in — so a user plan can never shadow a built-in in the list. `get_plan()` mirrors this by checking `DEPLOYMENT_PLANS` before a `get_item` on `planId`, and both `_get_user_plans` and `get_plan` swallow `ClientError` to fall back to built-ins. The create path enforces the same precedence a second time: `create_deployment_plan` recomputes `builtin_ids` from `get_all_plans()` and returns 409 on a built-in collision, and 409 on an existing user id unless `overwrite=true`. Built-in ids exactly match the deployer's `plan_compose_map` keys (seven each), so there's no drift between "what the API considers built-in" and "what the deployer resolves by hardcoding."

One asymmetry: `get_all_plans` skips a colliding user plan but never deletes it, so a stale user row with a built-in id can persist invisibly in the table. Harmless for reads (built-in wins), and the create path blocks producing such a row, so it's only reachable via out-of-band writes — noted, not blocking.

### Deployer resolution for user plans

```
deployment_plan (booking) ──► in plan_compose_map?
        │ yes                         │ no
        ▼                             ▼
  hardcoded compose_file      _get_plan_record(planId) from DynamoDB
  + PLAN_MODEL_MAP model      compose_file = record.composeFile or fallback
                              model_name  = record.modelName  or fallback
                                    │
                                    ▼
                      _load_compose_content(compose_file)
                      (reads s3://COMPOSE_BUCKET/compose-files/<file> first)
```

The `instanceType` the poller needs is not resolved here — it's captured at booking-creation time, where `create_booking` sets `instanceType = plan.instanceType` via `get_plan()`, which now resolves user plans, so the spot-type request carries the uploaded plan's instance type end to end.

The `or fallback` on both fields means a user record missing `composeFile` silently falls back to `docker-compose.yaml` (the built-in default) rather than failing — reachable only via a malformed row since create always writes a `composeFile`, but worth knowing because it fails toward a wrong deployment rather than an error.

### Input validation and the code-execution surface

`create_deployment_plan` enforces the guardrails that matter for an upload that ends up executed on a GPU host: `instanceType` must be in `ALLOWED_INSTANCE_TYPES`, content is rejected over 512 KB, the `planId` is a slug of `[a-z0-9-]` derived from the name, and the derived filename `user-<planId>.yaml` is re-checked for `/`, `\`, and `..` so it can't traverse outside `compose-files/`.

The gap is YAML validation. With PyYAML present, `yaml.safe_load` must yield a non-empty dict. Without it, the fallback accepts the document if it merely contains the substring `services` anywhere, or if any non-comment line contains a `:` — passing almost any text, including content that isn't a compose file. Because the artifact is later run via SSM on the host, "is this actually a compose document" is a security-relevant check, not just a UX nicety. Bundling PyYAML (the code already prefers it) or tightening the fallback to require a top-level `services` mapping would close it. Admin-only behind Basic auth makes this a hardening item rather than an open exposure, but it should be fixed given the blast radius.

### API ↔ CDK contract

The CDK sets `COMPOSE_BUCKET` and `DEPLOYMENT_PLAN_TABLE` on the API Lambda and `DEPLOYMENT_PLAN_TABLE` on the deployer, matching the `os.environ.get` reads. The table pk `planId` matches every `Key={"planId": ...}` access. The stack adds `/deployment-plans` (`GET`,`POST`) and `/deployment-plans/{planId}` (`DELETE`), and the router has a branch for each with the same resource strings and methods. IAM: the API role gains `s3:PutObject/DeleteObject/GetObject` on the compose bucket and DynamoDB rw on the plan table ARN; the deployer role gains `dynamodb:GetItem` on the plan table and already holds `s3:GetObject` on the compose bucket. `composeBucket` is declared earlier in the stack, so the new references are in scope.

### Failure modes in create/delete

Create writes S3 then DynamoDB. A `put_item` failure after a successful `put_object` leaves an orphaned `compose-files/user-<planId>.yaml` with no plan row pointing at it — a storage leak, not a correctness bug, but the delete-on-failure (or table-first ordering) is cheap to add. Delete is the inverse and best-effort on the S3 side: it removes the table row authoritatively and only logs a warning if the S3 delete fails, so a missing object doesn't block plan removal. Delete also refuses built-in ids up front (`400`), a second enforcement point beyond the UI gating.

### Frontend correctness and contract match

Nav item and breadcrumb for `/plans`, a route to `PlansPage`, and a table that renders `source` as a tag and gates the delete action so built-in rows show a disabled button while user rows get a `Popconfirm`. BookingPage picks up new plans automatically because it reads `deploymentPlans` from `GET /status`, which calls `get_all_plans()`; its label now appends "(自定义)" for `source === 'user'`.

Two rough edges. First, error surfacing: the shared `request()` helper special-cases every 409 by throwing `new Error('Conflict')` with the parsed body on `.data`, but `handleSubmit` displays `error.message` — so a duplicate-id or built-in-collision upload shows "Conflict" instead of the specific reason the API returned. Reading `error.data.error` on the plans page (as the booking flow does for its conflict) would restore the detail. Second, `deleteDeploymentPlan` interpolates `planId` into the URL path without `encodeURIComponent`; ids are currently slugified so this is safe, but it's a latent correctness issue if id derivation ever changes. The `overwrite` field exists in the request type but the page never sends it, so re-uploading a same-named plan 409s with no UI path to replace — acceptable for v1, but the generic error message makes it look like an unexplained failure.
