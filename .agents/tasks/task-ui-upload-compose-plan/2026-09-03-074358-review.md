## High-level view

The v1 security finding — the YAML fallback being a near-no-op — is the substantive one, and it is properly closed. `_validate_compose_content` now requires a dict `services` section under the PyYAML path, and the PyYAML-absent path delegates to a new `_fallback_has_services_mapping` that demands a real top-level `services:` mapping: block form with at least one indented child, or a non-empty inline mapping that explicitly rejects `{}`. The stated behavioral matrix (valid block/inline pass; non-compose text, `services: {}`, bare `services:`, commented-out services, empty string all fail) matches what the code does on read-through.

The remaining four findings are mechanical and each lands where expected: the S3 object is best-effort deleted on the `put_item` failure path before the 500 returns; `PlansPage.handleSubmit` now reads `error.data?.error` before falling back to `error.message`, restoring the specific 409 reason while leaving the shared client's 409 behavior (and the BookingPage conflict flow) untouched; `deleteDeploymentPlan` wraps the id in `encodeURIComponent`; and `recipe` is still persisted but now documented as reserved-for-future-deployer-use rather than silently dead.

The contract verified in v1 still holds unchanged: table pk `planId`, the `COMPOSE_BUCKET`/`DEPLOYMENT_PLAN_TABLE` env vars on both Lambdas, the three routes with matching router branches, and IAM (S3 rw for the API, DynamoDB `GetItem` for the deployer). None of the v2 edits touch the merge/collision, deployer resolution, or route wiring, so the earlier verified-correct behavior carries forward.

### Finding 1 — YAML validation fallback (resolved, confirmed)

The PyYAML path now goes beyond "non-empty dict": after `yaml.safe_load`, it requires `parsed` to be a dict and `parsed.get("services")` to be a non-empty dict. The fallback for the PyYAML-absent case (the default on the Lambda runtime, since this asset has no vendoring step) is a genuine structural check. `_fallback_has_services_mapping` scans for a top-level line (no leading whitespace) starting with `services:`, then:

- inline form (`services: {...}`): accepts only when the remainder opens a mapping and is not `{}`, and rejects a trailing comment — so `services: {}` and `services: # comment` both fail;
- block form (`services:` with nothing after): accepts only if the next non-blank, non-comment line is indented; a bare `services:` at end of file, or immediately followed by another top-level key, fails.

Blank and comment lines are skipped in both the outer scan and the child scan, so a commented-out `# services:` never triggers acceptance. This closes the v1 gap where any text containing the substring `services` or any `:`-bearing line passed. The residual edge: block-form validity is inferred purely from indentation of the following line, so the check confirms shape, not semantic validity — a reasonable floor before PyYAML, which is still preferred when importable. Strictly a tightening; no regression.

### Finding 3 — orphaned S3 object on failed metadata write (resolved, confirmed)

`create_deployment_plan` still writes the compose object to S3 before `put_item`. On a `put_item` `ClientError`, it now issues a best-effort `s3.delete_object` for the same `compose-files/{compose_file}` key inside the failure branch (the `s3` client is in scope from the earlier `put_object`), logging a warning if the cleanup itself fails, before returning 500. This removes the v1 storage-leak path. The cleanup is best-effort and not retried, which is appropriate since the operation already failed and the caller gets a 500 regardless.

### Finding 2 — 409 detail lost in the client (resolved, confirmed)

The shared `request()` helper is unchanged: it still throws `new Error('Conflict')` with the parsed body attached on `.data` for every 409. The fix is local to `PlansPage.handleSubmit`, which now types the caught error as `Error & { data?: { error?: string } }` and surfaces `error.data?.error || error.message || '上传部署方案失败'`. A built-in collision or existing-id 409 now shows the API's specific message ("collides with a built-in" / "already exists; set overwrite=true") instead of a bare "Conflict". Leaving the shared client untouched keeps the BookingPage conflict flow (which reads `error.data` directly) unaffected. `handleDelete` still surfaces only `error.message` — fine, since the delete path returns 400/404/500, handled by the `!response.ok` branch as `API Error <status>: <text>`, not 409.

### Finding 5 — DELETE path id not URL-encoded (resolved, confirmed)

`deleteDeploymentPlan` now builds the path as `/deployment-plans/${encodeURIComponent(planId)}`. Ids remain slugified to `[a-z0-9-]`, so this is defensive rather than load-bearing today, but it matches the finding.

### Finding 4 — `recipe` accepted but unused (resolved as documented, confirmed)

The coder kept persisting `recipe` and added a comment in `create_deployment_plan` stating it is reserved: the deployer resolves user plans by `composeFile` + `modelName` only, and `recipe` is stored so the record shape matches built-in plans and a future deployer change can consume it without a data migration. The deployer diff confirms it reads only `composeFile`/`modelName` from the record. This was the softest of the five findings ("drop it or wire it"); documenting the intent removes the "misleads the reader" concern.

### Regression scan on unchanged behavior

The v2 edits are confined to validation, the create failure path, and frontend error/id handling. The built-in-vs-user merge (`get_all_plans`/`get_plan`), the deployer's `plan_compose_map` gate and record lookup, the router branches, the CDK table/IAM/env/route wiring, and `models.py`'s `source` default are byte-for-byte what v1 reviewed and verified. `create_deployment_plan`'s collision checks (builtin ids, existing user id unless `overwrite`) and the `overwrite` type field (present, still not sent by the page) are unchanged — the same accepted-for-v1 posture. No new code path bypasses the allowlist, size cap, or slug/filename sanitization.
