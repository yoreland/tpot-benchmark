# Preview DeepSeek-V4-Flash-DSpark on B300: whole-machine TP8 vs 4P4D PD run summary (v1)

This change set is the deliverable of a live operational benchmark, not a code change: six task-state JSON files that plan and record the run, plus one run-summary markdown (`b300-sglang-preview-dspark-tp8-vs-4p4d-20260914-summary.md`). The run served the preview `deepseek-ai/DeepSeek-V4-Flash-DSpark` (SGLang v0.5.17-cu130, fp8/mxfp4, DSPARK spec-decode) on one 8x B300 in two topologies — whole-machine TP8 and hand-built 4P4D native PD (nixl, DSpark on decode) — over the identical 40k-in/1.5k-out sweep (c=1/2/4/8/16), and compared TPOT/ITL. "Correctness" here is whether the summary and feature findings faithfully, consistently, and honestly reflect what happened on the instance. The tables match the orchestrator-verified raw JSONL, the DSpark-acceptance caveat is handled with real honesty, and the boundaries (instance/booking left running, no teardown) were respected.

Watch for: (1) the comparison table (c) has two unbolded winning cells at c2 — TP8 wins `out tok/s` (573.3 vs 523.9) and `ITL p99` (2.60 vs 7.85) but neither is bolded, so the bolding contradicts the prose that says TP8 leads throughput at c2 (confirmed). (2) The "TP8 wins ITL median" claim compares a direct-to-engine ITL against a router-measured ITL that is almost certainly per-decode-*step*, not per-token, so the two ITL-median columns are not a like-for-like latency (likely). Neither undermines the headline verdict; both are report-accuracy fixes.

**Verdict**: NEEDS_CHANGES

## High-level view

The four features form a clean dependency chain: download the preview weights once (FEAT-001), bring up TP8 and sweep (FEAT-002), tear TP8 down and hand-build 4P4D PD reusing the same weight copy and sweep (FEAT-003), then collect and compare (FEAT-004). Every feature is `completed`, every acceptance criterion is addressed in findings, and the summary faithfully carries forward the numbers recorded in the feature findings — which in turn match the raw JSONL the orchestrator re-pulled from the instance.

The headline verdict — 4P4D wins TPOT (flat ~1.3 ms vs TP8 climbing to 15 ms at c16) and the ITL p99 tail (<=11 ms vs TP8 c16 507 ms), at the cost of much higher TTFT (c16 ~22 s vs ~4.2 s) and higher ITL median — is supported by the data and stated with the right hedging. The report is honest that this is the opposite of the prior vLLM PD run, and it does not overclaim throughput (correctly saying it is "roughly comparable").

The one substantive honesty item is well handled: DSpark acceptance is directly observable only on TP8 (accept length 5.47–5.76), not through the PD router, and the report carries an explicit caveat that a slice of the TPOT/ITL delta could be an acceptance difference rather than topology alone. That caveat is the right call.

The defects are narrow and mechanical: two winning cells at c2 aren't bolded (the table's own "bold = winning" contract), and the ITL-median comparison quietly mixes a direct-engine measurement with a router measurement that the arithmetic shows is per-step. Fixing the bolding and adding one sentence qualifying the ITL-median column would make the report fully self-consistent.

### Bolding contract broken at c2

Table (c) declares "bold = winning cell" and then applies it correctly at every level except c2. At c2, TP8 wins `out tok/s` (573.3 vs PD 523.9) and `ITL p99` (2.60 ms vs PD 7.85 ms), but both cells are left unbolded:

```
| 2 | 573.3 → 523.9 | 2.36 → **1.26** | 4.05 → **2.12** | **1.29** → 7.10 | 2.60 → 7.85 | **1692** → 2852 |
```

This is confirmed against both the summary's own tables (a)/(b) and the FEAT-002/003 findings. It is self-contradicting in two ways. First, the throughput verdict prose explicitly says "TP8 leads only at c2" — so the author knows TP8 wins that cell, yet the table doesn't bold it. Second, the ITL p99 reading note handles c1 ("At c1 TP8's ITL p99 (2.36 ms) is still lower than PD's (7.20 ms), so that cell bolds TP8; the PD ITL p99 win only emerges from c4 up") but silently skips c2, where TP8 also wins ITL p99 (2.60 < 7.85). The fix is mechanical: bold the two TP8 c2 cells, and extend the reading note to say TP8's ITL p99 win covers c1 *and* c2.

### ITL median: direct-engine vs router measurement

The verdict lists "ITL median: TP8 wins" as a peer of the other four criteria, explained as: TP8 emits 5–6 accepted tokens per verified DSpark step so the typical inter-token gap is ~1.2–2.0 ms, whereas the PD router shows a steady ~7.1 ms cadence. The report attributes PD's 7.1 ms to "the PD router measures a steady ~7.1 ms inter-token cadence," which is the key admission — but it's buried, and the verdict still frames this as a straight TP8 win.

The arithmetic makes the mismatch concrete. On PD, ITL median is 7.1 ms and TPOT median is 1.3 ms. If ITL were per-token, TPOT (mean per-token) could not be ~5x lower than the ITL median. The only consistent reading is that the router's ITL sample is the wall gap between streamed *steps* (each carrying ~5–6 accepted tokens), so 7.1 ms / ~5.5 ≈ 1.3 ms ≈ PD TPOT. TP8's direct-to-engine ITL, by contrast, tracks per-token gaps (~1.2–2.0 ms). So the two ITL-median columns measure different things, and "TP8 wins ITL median" is not a like-for-like user-latency statement. This doesn't change the headline (TPOT, ITL p99 tail, TTFT are all unaffected and the verdict rests on those), but the ITL-median line should be qualified so a reader doesn't conclude PD delivers 6x worse typical token latency when the gap is largely a measurement-granularity artifact.

### The same arithmetic bounds the DSpark caveat

The DSpark caveat — acceptance is 5.47–5.76 on TP8 but "not observable through the PD router," so "a slice of any TPOT/ITL delta could therefore reflect a spec-decode-acceptance difference rather than the topology alone" — correctly flags a spec-decode/acceptance trust boundary that couldn't be measured on the PD side. It is slightly over-pessimistic, though: the 7.1 ms-step / 1.3 ms-token relationship above is itself indirect evidence that PD decode is accepting ~5.5 tokens/step, i.e. comparable to TP8. The report already gestures at this ("the flat ~7.1 ms ITL / ~1.3 ms TPOT are consistent with strong acceptance") but stops short of the quantitative bound. Adding the ratio would let the caveat say the acceptance-driven slice of the delta is probably small, which is both more useful and still honest.

### Numbers are faithful; TP8 throughput is non-monotonic

Every table cell traces cleanly through the chain: summary table (a) == FEAT-002 findings; table (b) == FEAT-003 findings; the orchestrator re-pulled the JSONL and confirmed TP8 c16 (TPOT med 15.02 / ITL p99 507.52 / out 763.33), PD c16 (TPOT med 1.32 / ITL p99 8.48 / out 917.70), and TP8 c1 accept 5.74 match exactly. Minor rounding (TTFT c16 4206.86 in table (a) vs "4207" in findings) is immaterial. Table (c)'s per-cell values are transcribed correctly from (a)/(b) apart from the bolding gap above.

One artifact worth a one-line acknowledgment: TP8 `out tok/s` is non-monotonic — 356.5 → 573.3 → 511.8 → 780.0 → 763.3, dipping at c4 and again at c16. This is real measured data (verified in the JSONL), not a transcription error, but the report presents the numbers without comment, and a reader scanning the table may read the c4 dip as a mistake. A short clause ("TP8 throughput is non-monotonic across the sweep, reflecting prefill/decode contention on the shared cards") would preempt that.

### Boundaries and faithfulness to the request

The boundary contract was respected: FEAT-001–004 findings and the summary's "Not done (by design)" section all state the instance, both topologies' servers (currently the PD engines + router), and booking `5bd1f130` were left running for the orchestrator's teardown decision — matching the environment constraint that irreversible teardown is not the agent's call.

The work answers the user's request ("整机 + 4p4d", test the preview v4 flash DSpark in both whole-machine and 4P4D and compare): both topologies were served on the same weight copy with an identical sweep, DSpark was confirmed active in both (TP8 accept 5.47–5.76; PD via decode startup logs on all 4 decode ranks), and the comparison is delivered with three tables and a verdict. The single-weight-copy reuse honors the scarce-B300 constraint, and the explicit `--gpus device=` pinning avoided the prior vLLM run's `--gpus all` collision (verified clean 0-3/4-7 split).
