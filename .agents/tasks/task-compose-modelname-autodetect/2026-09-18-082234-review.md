# Auto-derive modelName from compose so the download path matches the container's read path (pass v1)

The deployer downloads HF weights to a directory built from a plan's `modelName`, but a user-uploaded compose file pins the weights to `/opt/dlami/nvme/models/<slug>` (slug = HF repo id with `/`→`__`). When a user uploaded a compose referencing a model the deployer had never seen and left `modelName` empty or wrong, the download dir and the dir the container reads diverged, health never passed, and the booking failed. The fix adds a PyYAML-free `extract_model_from_compose()` that scans the compose text for the pinned path and makes it the source of truth: the deployer now derives the model from the actual compose content (compose > plan `modelName` > `DEFAULT_MODEL_NAME`) right before building the download command, and the API upload path derives the persisted `modelName` the same way (compose > body `modelName` > `DEFAULT_PLAN_MODEL`). The helper is intentionally duplicated in both Lambda packages because they ship as separate assets with no shared import path.

Watch for: nothing blocking. The download path is now guaranteed to match the container path because both come from the same compose text loaded once (**confirmed**). Minor edge: the derived model string is interpolated into a shell/Python `snapshot_download(...)` command without escaping, so an exotic slug could in principle break the command — but the HF slug charset makes this near-impossible in practice (**possible**). The volume-mount / `:ro` suffix case is not stripped by the regex delimiter set (**possible**).

**Verdict**: APPROVED

## High-level view

The real fix lives in the deployer, not the API. `_get_compose_commands` loads the compose text once (from S3 for user plans, local bundle for built-ins), derives the model from it, and builds both the `snapshot_download` id and the `local_dir=` path from that single derived value. Because the container reads the path the compose itself pins, deriving from the same text closes the gap structurally — even a stale or wrong stored `modelName` self-corrects at deploy time. The API-side derivation is defense-in-depth: it keeps the persisted record (and the UI) honest, but is not what unbreaks the booking.

The parsing contract is deliberately narrow and text-only: a regex captures the first path segment after `models/`, dedups slugs preserving first-seen order, warns (never raises) on conflicting slugs, and inverts only the first `__` back to `/`. Zero matches returns `None` so callers fall back. This matches every one of the 7 built-in compose files back to the exact `PLAN_MODEL_MAP` value, so built-ins and existing user records are unaffected.

Test coverage is strong for a pure-function fix: the extractor is exercised against both duplicated copies (asserting they stay in lock-step), against all 7 real built-in compose files, and the deployer's real `_get_compose_commands` is driven with a stubbed loader to assert the generated `snapshot_download` id and `local_dir=` — the exact bug surface. The API's `create_deployment_plan` is not run end-to-end (no moto); its decision is tested via a replica, which is a known seam rather than the real branch.

### The fix lands at the deployer, where the download path is actually built

The download-vs-read mismatch is a deployer-side symptom, and that is where the authoritative fix sits. `_get_compose_commands` now loads the compose content once and feeds it to both the extractor and the heredoc that writes the file onto the box, so the model used for `snapshot_download` and the `/opt/dlami/nvme/models/<slug>` directory the container mounts are derived from the same bytes. For user plans that content comes from S3 (`_load_compose_content`), so whatever the user actually uploaded drives the download path — a wrong or empty stored `modelName` can no longer desync the two. The resolution order (compose-derived → passed `model_name` → `DEFAULT_MODEL_NAME`) with a warning when a non-empty passed value is overridden is the right precedence: the compose file dictates the directory the container reads, so it must win.

```
compose text (S3 for user plans / bundle for built-ins)
        │ loaded once
        ├─ extract_model_from_compose ─► model_name ─► snapshot_download(model_name)
        │                                          └─► local_dir=/opt/.../<slug>
        └─ heredoc ─► compose file on box ─► container reads /opt/.../<slug>
                              (same slug on both sides ⇒ health passes)
```

The API upload derivation is a secondary consistency guarantee, not the fix. Persisting the compose-derived `modelName` keeps the plan record and UI aligned with what will deploy, but even if it stored the wrong value the deployer would self-correct. Worth noting the two layers use different fallbacks (`DEFAULT_MODEL_NAME` vs `DEFAULT_PLAN_MODEL`); both resolve to `deepseek-ai/DeepSeek-V4-Flash` today, and the tests pin both constants, so a future divergence would be caught.

### Slug parsing contract and its edges

The extractor captures `/opt/dlami/nvme/models/([^\s'\"\\/]+)`. Warn-don't-raise on conflicting slugs is a deliberate fail-soft choice for a deploy path — a malformed multi-model compose still deploys against the first model rather than hard-failing the booking. Inverting only the first `__`→`/` is the correct HF slug inversion: the org has no `__`, but a model name legitimately can (`org__name__with__extra` → `org/name__with__extra`).

The delimiter set omits `:`, so a path written as a docker volume mount with a `:ro`/`:/container` suffix would be captured with the suffix attached. No built-in or documented user form writes the model path that way, so this is a latent gap rather than a live bug — worth a comment or an added delimiter if arbitrary user composes are expected to use volume syntax.

The derived string then flows unescaped into `snapshot_download('{model_name}', local_dir='{model_local_path}')` embedded in a bash `-c`. HF repo ids are constrained to a safe charset, so this won't bite in practice, but the value now originates from arbitrary user-uploaded text; a slug carrying a `'` would break out of the Python string literal. A cheap guard rejecting slugs outside `[A-Za-z0-9._/-]` before interpolation would remove the ambiguity entirely.

### Backward compatibility for built-ins and existing records

The concern with any "derive from content" change is whether it silently reclassifies existing plans. It doesn't. Built-in plans keep their hardcoded `PLAN_MODEL_MAP` resolution and never reach the user-plan branch, and the tests assert every one of the 7 built-in compose files parses back to exactly the `PLAN_MODEL_MAP` value that plan already used — so the derived value equals the prior value and nothing changes for them. Existing user records still carry their persisted `modelName`, but since the deployer now prefers the compose-derived value, a previously-broken record is repaired on the next deploy without any migration.

### Test coverage

The extractor is well guarded: both duplicated copies are run through every case and asserted identical (so the intentional duplication can't drift), all three real path forms (SGLang `--model-path`, vLLM `--model`, shell `MODEL=`) are covered, and the conflict/dedup/first-`__` rules each have a case. The deployer bug surface is tested against the real `_get_compose_commands` with only `_load_compose_content` stubbed, asserting the generated `snapshot_download` id and `local_dir=` — this is the assertion that would fail if the precedence wiring were reverted.

Not tested: the API's real `create_deployment_plan` branch. It's exercised through a hand-written replica (`_resolve_upload_model_name`) rather than the function itself, so the real branch could be edited to diverge from the replica without any test catching it. The deployer side sets the bar by testing the real function; the API side would benefit from the same. Also untested (and acceptable given intent): the `:`-suffixed volume-mount form and any unescaped-slug interpolation, since no supported compose form produces them.
