# One-click GPU booking platform with CDK deployment

This change introduces a complete GPU booking platform under `platform/`. A React SPA backed by API Gateway + Lambda lets customers select a deployment plan (instance type + docker-compose recipe), fires a booking into DynamoDB, and kicks off a periodic poller Lambda that attempts spot instance launches across us-east-1, us-east-2, and us-west-2. Once an instance reaches "running," an EventBridge-triggered deployer Lambda pushes docker-compose via SSM, health-checks port 30080, and writes the OpenAI-compatible endpoint back into the booking record. Notifications go out over SNS (email) and Feishu (webhook HTTP POST). IP whitelisting is enforced by per-instance security groups on port 30080.

Watch for: The poller and deployer Lambdas have no EventBridge rules wiring them up (confirmed). The front-end API client sends `deploymentPlanId` in the booking POST body but the backend reads `deploymentPlan` (confirmed). The API handler Lambda lacks EC2 permissions but calls `terminate_instance` and `update_security_group` (confirmed). The deployer can exceed Lambda's 15-minute maximum if SSM wait + deployment + health-check timeouts stack up (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The CDK stack declares DynamoDB tables, three Lambdas, an API Gateway with a Basic Auth token authorizer, S3+CloudFront for the SPA, and SNS. It does *not* declare the EventBridge rules that would actually trigger the capacity poller on a schedule or the deployer on EC2 state change events, so after deployment both Lambdas sit idle.

The API handler routes through a single Lambda with a manual path-based router. It imports `ec2_manager` to terminate instances and manage security groups, but the Lambda's IAM role has no EC2 permissions — every whitelist update and booking cancellation involving a running instance will fail with Access Denied.

The capacity poller hard-codes subnet IDs, AZ mappings, and max spot prices. It scans for `status=polling` bookings and attempts direct `RunInstances` with spot options. There is no concurrency guard: two concurrent poller invocations can both read a booking as `polling` and launch duplicate instances.

The deployer's internal timeouts (SSM wait 300s + deploy 600s + health-check 600s = 1500s) far exceed the Lambda's 10-minute configured timeout. When Lambda kills it mid-flight, the booking is stuck in `deploying` with the instance running and billable.

The frontend sends `deploymentPlanId` in the POST body but the backend reads `deploymentPlan`. The `listBookings` endpoint returns `{ bookings: [...] }` but the client expects a raw array. Both mismatches make the booking flow and monitoring pages non-functional.

1. **Missing EventBridge rules** (confirmed) — The CDK stack declares poller and deployer Lambdas but creates no schedule rule or EC2 state-change rule. Neither Lambda will ever be invoked. Add `events.Rule` resources in CDK.
2. **Frontend/backend field name mismatch** (confirmed) — The React client POSTs `{ deploymentPlanId }` but `create_booking` reads `body.get("deploymentPlan")`. Bookings always fail plan validation. Align to one name.
3. **API handler missing EC2 IAM permissions** (confirmed) — `ApiHandlerRole` has no `ec2:*` statements, but the handler calls `terminate_instance` and `update_security_group`. Add EC2 permissions to the role.
4. **Deployer timeout exceeds Lambda max** (confirmed) — Internal timeouts sum to 1500s vs Lambda's 600s configured / 900s hard cap. Split into a Step Functions workflow or use DynamoDB-tracked state with multiple short invocations.
5. **Poller race condition: duplicate launches** (likely) — No conditional DynamoDB update guards against two poller invocations processing the same booking. Add `ConditionExpression: status = polling` on the status update.
6. **API listBookings response shape mismatch** (confirmed) — Backend returns `{ bookings: [...], count }` but frontend expects `Booking[]`. Monitoring and History pages will render empty. Unwrap in the client or flatten the backend response.
7. **Orphaned security groups on termination** (confirmed) — `delete_booking` terminates the instance but never deletes the per-instance security group. These accumulate toward the VPC SG limit. Add cleanup in the termination path.
8. **No SSM permissions on EC2 instance profile** (possible) — The poller references `tpot-bench-ec2-profile` by name. If that profile lacks `AmazonSSMManagedInstanceCore`, SSM RunCommand in the deployer will fail. Verify the external profile or create it in CDK.
9. **Feishu webhook test CORS failure** (likely) — `SettingsPage` sends the webhook POST directly from the browser. Feishu servers unlikely to return CORS headers. Route the test through the backend.
10. **Hardcoded account ID and subnet IDs** (confirmed) — `bin/app.ts` and `poller/handler.py` contain literal account ID and subnet IDs. Parameterize via CDK context or SSM parameters.

## Missing trigger wiring in CDK

The CDK stack creates `capacityPoller` and `deployer` Lambda functions with proper IAM roles, but never adds:

- An `events.Rule` with a `schedule` source to invoke `capacityPoller` periodically (the poller's docstring says "Triggered by EventBridge on a schedule").
- An `events.Rule` with an EC2 state-change event pattern to invoke `deployer` (the deployer's docstring says "Triggered by EventBridge rule monitoring EC2 instance state changes").

Without these rules, bookings enter `polling` state and stay there permanently.

## Field name mismatch between frontend and backend

In `frontend/src/api/client.ts`:

```typescript
body: JSON.stringify({ deploymentPlanId, confirmOverride }),
```

In `lambda/api/handler.py:create_booking`:

```python
deployment_plan_id = body.get("deploymentPlan", "")
```

The backend reads `deploymentPlan`, the frontend sends `deploymentPlanId`. Every booking attempt will fail with "Invalid deployment plan" because `get_plan("")` returns `None`.

## Deployer timeout arithmetic

The deployer Lambda is configured with a 10-minute timeout in CDK:

```typescript
timeout: cdk.Duration.minutes(10),
```

But its internal timeouts stack sequentially:

```
_wait_for_ssm:     SSM_WAIT_TIMEOUT = 300s
_run_command:      timeout = 600s (passed in call)
health-check loop: HEALTH_CHECK_TIMEOUT = 600s
─────────────────────────────────────────────
worst case total:  1500s (25 minutes)
```

When Lambda kills the function mid-health-check, the booking remains in `deploying` state with no recovery mechanism. The instance stays running and billable.

## API response shape vs frontend expectations

`handler.py:list_bookings` returns:

```python
return _response(200, {"bookings": items, "count": len(items)})
```

`client.ts:listBookings` declares:

```typescript
export async function listBookings(status?: string): Promise<Booking[]> {
  return request<Booking[]>(`/bookings${params}`);
}
```

The frontend expects a raw array but gets `{ bookings: [...], count: N }`. `MonitoringPage` and `HistoryPage` will both fail to render data.

## Poller concurrency race

There is no concurrency guard on the poller. If EventBridge triggers it every minute and a previous invocation is still running, two invocations can both read the same booking as `status=polling` and both call `RunInstances`. The status update to `launching` after launch is unconditional:

```python
table.update_item(
    Key={"bookingId": booking_id},
    UpdateExpression="SET #s = :s, instanceId = :i, ..."
)
```

A conditional update (`ConditionExpression: #s = :polling`) would prevent the second invocation from succeeding, letting it skip instead of launching a duplicate.

## Missing EC2 permissions on API handler

The API handler imports `ec2_manager` which calls `ec2.terminate_instances`, `ec2.describe_instances`, `ec2.create_security_group`, `ec2.authorize_security_group_ingress`, and `ec2.modify_instance_attribute`. The `ApiHandlerRole` in CDK grants only DynamoDB, SNS, SSM, and S3. Every path that touches EC2 (booking deletion with a running instance, whitelist save on a `ready` booking) will return 500 with an AccessDenied wrapped in the generic error handler.

## Security group lifecycle on termination

`delete_booking` calls `terminate_instance` but never deletes the per-instance security group (`tpot-booking-<instance_id>`). `update_security_group` in `ec2_manager.py` creates these groups but nothing in the codebase ever calls `ec2.delete_security_group`. Over time these accumulate toward the VPC's default 2500 SG limit.

## Feishu webhook test bypasses backend

`SettingsPage` sends the webhook POST directly from the browser:

```typescript
await fetch(webhook, { method: 'POST', ... });
```

Feishu's servers don't return `Access-Control-Allow-Origin` headers for arbitrary origins. This call will be blocked by the browser's CORS policy. The test should route through the backend Lambda.
