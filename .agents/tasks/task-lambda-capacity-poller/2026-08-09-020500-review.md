# Lambda capacity poller for H200/B300 spot benchmarks

A Python 3.12 Lambda probes spot capacity across 3 regions and 8 AZs for p5en.48xlarge (H200) and p6-b300.48xlarge (B300) every 3 minutes via EventBridge. When a probe succeeds, it terminates the probe instance, renders a full bootstrap script (env prelude + recipe + bench-bootstrap.sh), uploads it to S3, launches the real benchmark instance with a lightweight user-data stub that fetches from S3, publishes an SNS notification, and disables the EventBridge rule. Deploy and teardown are idempotent bash scripts managing the full infrastructure lifecycle.

Watch for: IAM PassRole grants `iam:PassRole` to every role in the account (confirmed). The probe-then-launch pattern has a capacity gap where spot capacity can vanish between the successful probe and the real launch (likely). Security group lookup silently falls back to the VPC default SG, which may allow unexpected inbound traffic (confirmed). The rendered bootstrap concatenates two shebangs (confirmed, cosmetic).

**Verdict**: NEEDS_CHANGES

## High-level view

The IAM policy attached to the Lambda role gives `iam:PassRole` on `arn:aws:iam::*:role/*`, meaning any role in the account can be passed to any launched instance. This should be scoped to the specific instance profile role used by benchmark instances.

The core polling strategy is probe-then-terminate-then-launch: a bare spot request proves capacity exists, gets terminated immediately, and a second spot request launches the real workload. Between these two API calls the capacity may disappear, and the code does not retry or fall through to the next AZ when the second launch fails — it logs a warning and moves to the next instance type entirely.

The security group resolution silently selects the VPC default SG if `tpot-bench-noingress-sg` is not found in a region. In non-primary regions this fallback is likely to fire, potentially exposing the benchmark instance on unexpected inbound ports. The fallback should fail the probe for that region rather than proceed with weaker network posture.

SELF_TERMINATE is hardcoded to `false` and instances stay alive for SSH debugging. Cost bounding depends on `MAX_RUNTIME_MINUTES=240` being enforced by `bench-bootstrap.sh` — if the bootstrap crashes before reaching the timeout watchdog, the instance runs indefinitely at spot price.

<summary>Issues (5)</summary>

1. **PassRole scope too broad** — `iam:PassRole` resource is `arn:aws:iam::077090643075:role/*`. Scope it to the specific instance profile role (e.g., `arn:aws:iam::077090643075:role/tpot-bench-ec2-role`).
2. **SG fallback to default is fail-open** — `_get_security_group` returns the VPC default SG when the expected SG is missing. Return empty string (skip region) instead of falling back.
3. **Benchmark launch failure doesn't try next AZ** — When the real launch fails after a successful probe, the handler `continue`s to the next *instance type*, skipping remaining AZs for the current type. It should try the next AZ.
4. **Probe instance carries full instance profile** — The probe `RunInstances` call attaches `INSTANCE_PROFILE_NAME`, giving a short-lived throwaway instance credentials to the benchmark role. Remove the `IamInstanceProfile` param from probe calls since probes don't need AWS API access.
5. **Double shebang in rendered bootstrap** — `_render_full_bootstrap` concatenates an env prelude (which starts with `#!/usr/bin/env bash`) with the raw `bench-bootstrap.sh` (which also starts with `#!/usr/bin/env bash`). Functionally harmless but confusing in the uploaded S3 artifact.

<summary>Details</summary>

## IAM PassRole grants access to every role in the account

In `deploy-poller.sh` the inline policy's `IAMPassRole` statement uses:

```json
"Resource": "arn:aws:iam::077090643075:role/*"
```

This lets the Lambda pass any IAM role to any EC2 instance it launches. If the Lambda's code were ever modified — by a compromised deploy pipeline, an insider, or an accidental update — it could launch instances with admin-level roles. Scope this to `arn:aws:iam::077090643075:role/tpot-bench-ec2-role` (or the instance profile's backing role).

The `TerminateInstances` permission could additionally be narrowed with a `ec2:ResourceTag/Project` condition key to prevent terminating non-benchmark instances, though this is lower priority.

## Probe instance carries unnecessary credentials

`_probe_capacity` passes `IamInstanceProfile={"Name": INSTANCE_PROFILE_NAME}` on the probe instance. The probe's entire lifecycle is: launch, confirm it started, immediately terminate. It never needs AWS API access. During the window between launch and termination (and longer if the terminate call fails), the probe has credentials capable of reading the results bucket, writing to S3, and calling any API the instance profile grants.

Removing `IamInstanceProfile` from the probe call eliminates this. The probe exists solely to test whether `RunInstances` succeeds for that instance type and AZ.

## Security group fallback opens unexpected ports

```python
# Fallback: default security group
resp = ec2_client.describe_security_groups(
    Filters=[{"Name": "group-name", "Values": ["default"]}]
)
```

Using the VPC default SG as a fallback means the benchmark instance's network posture becomes unpredictable — it depends on whatever modifications have been applied to the default SG in each region. If the expected SG isn't found, the function should log an error and return empty string so the caller skips that region.

## Capacity gap between probe and real launch

The probe-then-launch sequence has a structural timing gap:

```
probe RunInstances -> success (capacity exists)
TerminateInstances probe
RunInstances real benchmark -> could fail (capacity gone)
```

When this happens, `_launch_benchmark` returns empty string. The handler then executes `continue`, which breaks out of the AZ loop entirely for the current target. Remaining AZs in `target["azs"]` that might still have capacity are never tried. The `continue` applies to the inner `for az in target["azs"]` loop but because it's inside a conditional block that ends with `break`, the semantics are: on probe success, either the benchmark launches and we `break`, or it fails and we `continue` — both exit the AZ loop.

The fix: restructure so that a failed `_launch_benchmark` falls through to the next AZ iteration instead of exiting the loop.

## EventBridge concurrency (possible)

The Lambda timeout is 120s and the EventBridge interval is 3 minutes, so invocations normally don't overlap. If Lambda retries an invocation due to throttling, two could run simultaneously, both find capacity, and both launch benchmark instances — double-spend. The probability is low given the 3-minute interval, but there's no distributed lock or idempotency token preventing it.

Confidence: **possible**.
