# Phase 0 prep for B300 PD 3P1D disaggregation

Adds a docker-compose file orchestrating 3 prefill engines (tp=2) + 1 decode engine (tp=2) + sglang-router on a single 8×B300 node, adds the `pd-3p1d-nixl` config case to the run-config script with a `--pd-compose` sentinel for the launch step to detect, and patches the capacity poller to include us-west-2b (the AZ where B300 was previously acquired). All parameter choices (image v0.5.17, env 16384, nixl backend, no dp-attention) are traceable to S3 failure logs.

Watch for: the `--pd-compose` sentinel in `CONFIG_SERVE_ARGS` is consumed by nothing yet — the launch/readiness/bench pipeline in `b300-run-config.sh` still assumes a single container (confirmed, the launch step will try to `docker run ... python3 -m sglang.launch_server --pd-compose`, which is not a valid server argument); no test coverage exists for the new config path (confirmed).

**Verdict**: APPROVED

## High-level view

The docker-compose file encodes the corrected parameters from the plan review (16384, nixl, no dp-attention, bootstrap ports on the router) into a ready-to-`docker compose up` YAML with healthchecks generous enough for a 30-minute cold start. `network_mode: host` means all five services share port space; collision is avoided by deliberate port spacing (30000/30100/30200/30300 for engines, 30080 for router).

The run-config addition uses `CONFIG_SERVE_ARGS="--pd-compose"` as a sentinel that the existing launch step doesn't understand. Running `--config pd-3p1d-nixl` today will produce a container that exits immediately on an unrecognized argument. The help text already advertises this config alongside working ones — an operator picking it will get a confusing failure rather than a clear "not yet implemented" message.

The poller fix adds us-west-2b (subnet + both instance type targets + log message update).

## The `--pd-compose` sentinel and the launch gap

In `b300-run-config.sh`, the `pd-3p1d-nixl` case sets:

```bash
CONFIG_SERVE_ARGS="--pd-compose"
```

The existing launch step (Step b) does:

```bash
docker run -d --name $CONTAINER ... $CONFIG_IMAGE \
  python3 -m sglang.launch_server $CONFIG_SERVE_ARGS
```

This produces `docker run ... python3 -m sglang.launch_server --pd-compose` — a container that exits with an unrecognized-argument error within seconds. `list_configs_indented()` already advertises `pd-3p1d-nixl` in `--help` alongside configs that work today. A two-line guard in Step b would make this explicit:

```bash
if [[ "$CONFIG_SERVE_ARGS" == "--pd-compose" ]]; then
    log "错误: $CONFIG requires docker compose (Phase 1 work). 当前脚本只支持单容器 docker run."
    exit "$EXIT_USAGE"
fi
```

## Router service over-provisioning

The router service mounts `/opt/dlami/nvme`, a `jitcache` named volume, and requests `shm_size: 16g`. A pure-Python router process doesn't load model weights, run CUDA kernels, or write JIT caches. The overhead is negligible (bind mounts are free), but it signals to a future reader that the router does heavy work — which it doesn't. Removing the NVMe mount and shrinking shm to the default would make the service's role clearer.

## Test coverage gap

The existing 27 cases / 258 assertions cover all five other configs via DRY_RUN. The `pd-3p1d-nixl` config has zero assertions. The plan review document's Phase 0 item 2 explicitly calls for DRY_RUN test cases asserting port assignments, bootstrap ports, router args, absence of `--enable-dp-attention`, and env=16384. None were implemented — regressions in parameter values (e.g., someone changing 16384 back to 8320) will not be caught automatically.
